# Reflection

This extension made the difference between “a feature appears on the screen” and “a feature is integrated” much clearer. Due dates and tags seemed small at first, but each decision affected the model, in-memory store, API contract, browser form, rendered cards, filters, and tests. Keeping the backend as the source of truth was the most valuable constraint. The browser never invents an overdue list or a tag-filtered subset; it asks `GET /tasks` for the result. That makes a refresh, another API client, and the UI agree on the same rule.

AI was most useful for quickly proposing a bounded plan and identifying repetitive edits across the model, endpoint, and UI. It was not reliable enough to accept without inspection. For example, an early suggestion classified every task with a past due date as overdue. That is plausible wording but incorrect for this tracker because completed work should remain historical rather than actionable. Another suggestion treated tags as browser-only display state, which would have broken persistence and API consistency. Reviewing those assumptions against user stories before coding prevented a more expensive correction later.

Preserving the Modules 1–3 behavior also mattered. The assignment is an extension, not a replacement, so I restored task-by-ID retrieval, strict workflow transitions, priority ordering, and drag-and-drop status updates. The transition rules are deliberately explicit: work starts before it is completed, completed work may be reopened, but a task cannot skip directly from `ToDo` to `Done`, return from `Done` to `ToDo`, or make a no-op move. The frontend sends a status-only PATCH on drop, so the API remains the single enforcement point.

The verification work changed my confidence more than the initial implementation did. Regression tests cover the baseline API behavior, while four focused mid-course tests cover date/tag behavior. Break tests demonstrated that the tests fail when the overdue comparison or Done-task exclusion is intentionally damaged. The final result stays intentionally small: no authentication, database, notifications, bulk actions, or other unrelated additions. That scope discipline made it feasible to verify the complete behavior rather than merely demonstrate a wider but less dependable prototype.
